## Упрощение по замечанию пользователя, 21 октября 2026

Причина серой кнопки: доступность браузерного редактора была связана с шаблоном, который
не создаётся для старых Excel-источников. Связь убрана; простой старый XLSX открывается без
переноса проекта. Прямая ссылка сразу открывает таблицу. «Сохранить изменения» выполняет
подготовку, проверку и применение без промежуточной навигации. Предупреждения подтверждаются
в этом же окне; ошибки не меняют исходные данные. История и подробные настройки свёрнуты.

Проверена именно книга `data_example`:25 листов и13219 формул на24 листах. Её нельзя безопасно
сохранять через текущий простой редактор. Теперь вместо неактивной кнопки — рабочий путь
скачивания оригинала/выбора исправленного файла с единым сохранением и проверками.
Настоящее браузерное редактирование и пересчёт такой книги остаются отдельной задачей.

Ручной браузерный прогон: старый XLSX без шаблона, открытие напрямую, одно сохранение, удаление
всех строк с отдельным подтверждением предупреждения, загрузка исправленной сложной книги
и применение из того же диалога. JavaScript без ошибок,390px в пределах окна. Артефакты:
`.backups/quick-edit-20261021-{legacy,warning,fallback-mobile,replacement-applied}.png`.
Это не независимые испытания экономистами; автоматические наборы остаются отложенными.

## Редактор дашборда: стабильность и сохранённые компоновки, 21 октября 2026

Причина повторного выталкивания соседей: `noCompactor` отключал уплотнение, но не
collision pushing. Добавлено `preventCollision: true`; обычное перетаскивание/изменение
размера не двигает другие карточки. В браузере соседние First/Second сохранили точные
координаты при перетаскивании Third вверх и при растягивании First вправо. Перемещаемый
виджет может остановиться на ближайшем доступном месте — занятое место не освобождается
автоматическим выталкиванием соседей.

Уплотнение вертикальных промежутков и подбор рекомендуемых размеров/рядов выполняются
отдельно, через обычный черновик и историю отмены. Проверены изменение, отмена и возврат
координат. Отдельный диалог размещения доступен из меню карточки; вставка в начало
однократно сдвигает остальных. Числовые координаты не допускают пересечения соседей.

Исходная компоновка защищена от перезаписи; текущие сохранённые дашборды не перестроены.
Ручной API-обход подтвердил атомарное сохранение именованного варианта, одинаковый ответ
повторного запроса, HTTP 409 устаревшей вкладке и неизменность исходного шаблона после
обычного сохранения. Браузерный обход создал дополнительный вариант, перезагрузил
страницу и восстановил исходную позицию Third (y=14). Ошибок JavaScript не зафиксировано.
При 390px диалог компоновок находится внутри экрана и прокручивается при необходимости.
Проверена сериализация/восстановление документа проекта с компоновкой: новые ID виджетов,
один исходный шаблон после последующего сохранения. Это не полный цикл создания выпуска.

Миграции проверены на чистом PostgreSQL и через откат/повтор новой миграции. Отдельная
новая миграция обратима на SQLite; старая начальная JSONB-миграция не поддерживает
весь чистый SQLite-цикл. Типы/API/линтер/форматирование и production build прошли.
Автоматические наборы по распоряжению владельца не запускались. Полная R6 не закрыта.

## Функциональный и UX-разбор, 21 октября 2026

Проверен основной путь экономиста: импорт → показатели/разрезы → предпросмотр →
сохранение → просмотр → замена исходных данных. Расчётная логика остаётся в графе;
исправления не меняют сохранённые проекты, формулы и размещение виджетов.

| Проблема | Влияние | Исправление |
|---|---|---|
| Завершение импорта возвращало только в список данных | P2: следующий шаг неочевиден | Создание отчёта с выбранным набором; при повторном открытии берётся активный снимок, а не устаревший снимок первого импорта |
| Мастер пропускал отсутствие показателей и несовместимые разрезы KPI/Bar/Line | P2: ошибка выявлялась только сервером | Объяснение и кнопки восстановления до расчёта, без скрытого удаления настроек |
| Вход в отчёт открывал редактор | P2: смешение чтения и изменения | Входные ссылки открывают просмотр, редактирование остаётся отдельным действием |
| Первый экран мог требовать контекст другого отчёта | P2: техническая ошибка при обычном входе | Предпочтение заполненной сводки без обязательного внешнего отбора; явная ссылка не переопределяется |
| Не выбран обязательный класс/другой отбор | P2: нормальная незавершённость выглядела как поломка | Понятная инструкция, доступные поля, расчёт не запускается до применения отбора |
| Контекстные параметры без старых bindings могли не показывать поля | P2: нет способа завершить настройку | Контролы доступны по объявленным параметрам; типы и неизвестные имена продолжают проверяться |
| Ошибка чтения дашбордов похожа на отсутствие отчётов | P2: риск лишнего создания | Отдельные загрузка/ошибка/пустое состояние и повтор чтения |
| Пустой или устаревший выбор набора не объяснял следующий шаг | P2: тупик мастера | Подключение данных или явный выбор актуального набора |

## R6: отмена раскладки и восстановление дашборда, 12 октября 2026

Браузерная проверка выявила три воспроизводимых P2-дефекта (ADR-185):

- После применения шаблона раскладки и редактирования заголовка команда отмены раскладки
  стирала заголовок. История теперь учитывает расположение и состав виджетов, сохраняя
  независимые названия, видимость, переходы и настройки дашборда. Редактирование названия
  после отмены не уничтожает возможность повторить раскладку.
- Пустой отчёт назначения с настроенным параметром не показывал поле его изменения.
  Существующая форма выбора теперь доступна и для пустого отчёта, в том числе в режиме просмотра.
- Изменение названия и возврат к сохранённому значению оставляли лишний локальный черновик.
  После успешного копирования диаграммы с потерей ответа сервера перезагрузка показывала
  старую диаграмму из этого черновика. Возврат к сохранённому состоянию теперь удаляет черновик;
  действительно несохранённые изменения и проверка ревизий сохраняются.

Регрессионные сценарии проверяют исходные координаты после отмены, сохранность заголовков и
навигации, повтор раскладки, сохранение/перезагрузку, URL-параметры и Back/Forward, потерю ответа
после commit и отсутствие повторно созданных узлов. Старые v1/v2-графы подготавливаются через
совместимые API; новый сценарий создания отчётов через публикации проверяется отдельно.
Это техническая проверка, а не замена испытаний с пятью экономистами или полного аудита WCAG.

## Дополнение: недоступное хранилище браузера, 10 октября 2026

ADR-173: регрессионный тест воспроизвёл потерю последних изменений — после отказа записи
возвращение к форме восстанавливало старый черновик. Отчёты и независимые визуализации теперь
сохраняют временную копию настроек и точного запроса в памяти документа. Она приоритетнее
устаревшей записи хранилища; ошибки quota/privacy остаются видимыми. Это не сохранение на сервере:
reload или закрытие вкладки уничтожают резервную копию. «Сохранить черновик и продолжить»
по-прежнему не разрешает переход, если запись не удалась. Неудачное явное удаление не уничтожает
резервный запрос. После подтверждённого сохранения старый запрос не восстанавливается при
Back/Forward, даже если очистка хранилища не сработала; сообщение явно говорит, что отчёт сохранён.

Три production-сценария `storage-unavailable.spec.ts` проверяют отказ записи, отказ чтения/записи/
удаления, новый черновик поверх старого, клиентские Back/Forward и потерю ответа после commit.
Повтор отправляет те же байты, оставляя ровно один отчёт/визуализацию. Отдельно проверено обычное
восстановление после reload с доступным хранилищем. Старые формы графа, раскладка дашборда,
вспомогательные диалоги и навигация между документами не покрываются этой гарантией.

## Дополнение: аналитические отчёты и сопоставление, 10 октября 2026

ADR-172 исправляет воспроизведённые регрессионными тестами P2: после добавления/удаления
группировок, показателей, фильтров и пар ключей пользователь терял контекст клавиатурного ввода;
в мастере сопоставления старая ошибка проверки полей могла скрывать новую ошибку предпросмотра.
Теперь Add/Remove направляет фокус к новому/соседнему полю, а перемещение группировки или
показателя — к перемещённому полю. При пустом списке фокус возвращается к Add. Идентификаторы,
точность, значения и порядок остальных элементов сохраняются. Обычный ввод не двигает фокус.
Ошибка проверки получает именованную локализованную панель; следующая попытка убирает старую
ошибку. В сопоставлении ошибки загрузки исходной схемы остаются отдельным состоянием.

`frontend/e2e/analytical-feedback.spec.ts` проверяет три production-сценария: аналитический отчёт
на ширине 760 px с клавиатурным добавлением/перестановкой/удалением, потерю ответа предпросмотра,
reload/восстановление и сохранение точного итога 0.30; создание и редактирование сопоставления
с двумя последовательными ошибками и успешной повторной проверкой. Ошибочные ответы в этих
сценариях задаются явно; успешные проверки исполняются реальным backend. Проверки не меняют граф.
Скрипт устанавливает фокус на кнопки перед Enter и автоматизированно выбирает поля: это не
полный последовательный Tab-аудит и не подтверждение WCAG или удобства для пяти экономистов.

Демонстрационная панель из восьми виджетов (ADR-171) теперь доступна через инструкцию README.
Следующий отдельный аудит: навигация с несохранёнными настройками при недоступном sessionStorage,
затем оставшиеся сквозные задачи, screen reader/контраст и человеческие испытания.

## Дополнение: мастера импорта и отчёта, 10 октября 2026

В production-сборке воспроизведён P2: после «Далее» и Tab фокус попадал на «Назад»,
пропуская поля нового шага. Исправление ADR-168 направляет фокус на заголовок шага,
включая продолжение после загрузки и завершение импорта. Заголовок не добавляет постоянную
остановку Tab; ввод данных и перевод интерфейса не перехватывают фокус.
Повторный прогон выявил гонку: после загрузки «Таблицы» кратко появлялись до перехода на
сохранённый импорт и повторно перехватывали фокус. Теперь следующий шаг показывает только
новая страница импорта; прежняя форма до перехода блокирует повторную загрузку.
На итоговом скриншоте обнаружено второе несоответствие визуальной системе: обычная таблица
отчёта показывала числа слева шрифтом 12 px. Теперь текст таблицы — 14 px; числовые столбцы
и заголовки выровнены вправо, цифры табличные. Решение опирается на логический тип поля,
поэтому строковые коды остаются слева. Форматирование значений, выбор строк и пагинация не менялись.

Сценарий `frontend/e2e/wizard-focus.spec.ts` объединяет импорт CSV, ошибочный тип поля и его
исправление, создание отчёта, замену суммы средним, обновление с перестановкой колонок и reload.
Проверяются точные значения 0.30 → 0.15 → 0.35 и сохранение кода 001 как текста.
Для действий используются Enter/Space, проверяется фокус после переходов и отдельные Tab-переходы.
Скрипт явно устанавливает фокус на часть контролов и задаёт файл/значения через автоматизацию:
это не доказательство полного обхода всего интерфейса только клавишей Tab или работы screen reader.
Сценарии запускаются для светлого desktop и компактного тёмного интерфейса; это не полный аудит
контраста, адаптивности или WCAG. Испытания с пятью экономистами всё ещё не проведены.

Дополнение ADR-169: ошибки действий импорта и проверки отчёта получают фокус и понятное
локализованное название. Новая попытка очищает прежнее сообщение: ошибка сохранения больше
не остаётся после успешной проверки, прежняя ошибка не скрывает более позднюю. Настройки
не сбрасываются. Добавление показателя/фильтра фокусирует новое поле; удаление — соседнее
поле или «Добавить», если список пуст. Обычный ввод не перехватывает фокус.
Регрессии сначала воспроизвели отсутствие фокуса; компонентные тесты проверяют также
оставшиеся значения и RU/EN/TT. Production-сценарий `wizard-feedback.spec.ts` обрывает
сохранение черновика, проверку полей, предпросмотр и ответ уже применённого импорта.
Повтор импорта посылает исходный запрос и оставляет один набор данных; повтор проверки
не создаёт расчёт. Тест использует явный focus/Enter и ввод значений автоматизацией,
поэтому не заменяет полное ручное клавиатурное прохождение или screen-reader аудит.

Дополнение ADR-170: мастер предлагает проверенные сервером результаты предыдущих формул
после итогов. Production-сценарий `summary-formulas.spec.ts` собирает цепочку «прибыль →
рентабельность → отклонение от цели» через именованные поля, сохраняет её, меняет первую формулу
и проверяет результат после reload. При прибыли 40.00 рентабельность равна 17.39, отклонение
от цели 20 — −2.61; после вычета ещё 10 — 30.00, 13.04 и −6.96. Каждый шаг использует
округлённый результат предыдущего шага с явно настроенной точностью. Устаревшие поля после
изменения зависимости скрываются до новой проверки. Проверка схемы не выполняет и не сохраняет
отчёт; API-регрессия отдельно подтверждает это для создания и редактирования, включая PostgreSQL.
Добавление/удаление формул всех трёх областей сохраняет фокус и идентичность оставшихся формул.
Это проверка конкретного сценария, не завершённая демонстрационная панель руководителя.

Следующие проверки: аналитический мастер и мастер сопоставления,
сохранность настроек при недоступном хранилище и все ещё открытые человеческие испытания.

## Границы решений

Проверка заполненности формы не заменяет серверную проверку типов и результатов.
Никакие суммы, соединения или значения полей не угадываются интерфейсом.
Подготовка данных остаётся в графе, визуализация использует опубликованный результат.
Ссылки публикаций, вычисления, API и сохранённые документы не преобразуются.

## Приёмка

- Unit/component: заполненность диаграмм, удалённые поля, скаляр, дополнительные серии,
  выбор и перемещение столбца при активном поиске; существующие тесты редактора и локализации.
- Browser: доступная загрузка, отмена удаления книги, подсказки вместо преждевременного
  запроса preview, настройка графика, клавиатурные вкладки, сохранение и пустой поиск.
  В этом коротком тесте публикация готовится API как fixture; это не доказательство
  сборки всего графа руками. Отдельные существующие table-authoring сценарии проходят
  Join по одному и нескольким ключам, вычисление, публикацию и дашборд через UI.
- Browser workspace: редактирование, серия, форматирование, порядок таблицы, копия,

## Беспристрастная оценка

Работа с уже подготовленными данными стала понятнее: меньше повторяющихся элементов,
ошибка не появляется до завершения обязательного выбора, следующий шаг обозначен явно.
Это подтверждённые изменения интерфейса, но не измеренное ускорение пользователя.

Подготовка сложного графа всё ещё требует понимания ключей Join, детализации данных,
агрегаций и публикаций. Интерфейс не делает эти аналитические решения автоматически.
Для больших графов остаётся нагрузка на поиск нужной ветки; текущая проверка не измеряла
работу новичка со 168 узлами. Полный аудит screen reader и проверка всех ошибок импорта
также не входят в доказательства этой сессии.

Следующий шаг оценки: дать экономистам одинаковые задания на двух версиях интерфейса —
загрузить две книги, объединить, рассчитать показатель, опубликовать и оформить три виджета;
затем изменить столбцы таблицы и исправить ошибочный выбор поля. Фиксировать время,
успешность, ошибочные действия и обращения за помощью. Порядок версий чередовать.
До такого испытания проценты ускорения и оценки «интуитивности» в баллах не заявлять.
