# P&L из четырёх книг в конструкторе

Это синтетический рабочий пример, а не перенос закрытых данных AlMaBi. Исходный ориентир:
[AlMaBi, dev](https://github.com/Alvik403/AlMaBi/tree/7b05260a480a8330fde33495d666af89e42d2149).
Используются обычные узлы и самостоятельные визуализации. Код отчёта на сервер не переносится.
Пользователи, переходы, иерархический drill-down и дополнительные панели фильтров не добавляются.

## Данные и явно выбранные правила

`backend/.venv/Scripts/python.exe fixtures/build_alma_demo.py` создаёт четыре публичные книги
в `fixtures/excel/` и независимые ожидаемые значения `alma-expected.json` (Decimal, без Polars).
Книги содержат январь–март двух лет, два направления, два товара в документе, убыток в январе,
разные суммы БУ/НУ и отсутствующий план февраля. Ни один пропуск плана не заменяется фактом.

| Правило / элемент исходника | Реализация в графе | Проверка |
|---|---|---|
| Бухгалтерский регистр | Excel Source, заголовок 3, пропуск 1, исключение последней строки | Исключены пояснение и искусственный итог 999999 |
| Реализация и затраты | Два левых Join, Document + Item, many-to-one | Две позиции документа не перемножаются; расходы без реализации сохраняются |
| Классификация счетов | Calculated Column, `if_else` по Account | 90.01: выручка; 44: коммерческие; 26: управление; 91.01/91.02: прочие |
| Себестоимость | Отрицательный Cost из отдельной книги | Пропуски для нерелевантных строк явно заменены нулём |
| Показатели БУ/НУ | Раздельные Revenue BU и Revenue NU | Суммы не подгоняются друг под друга |
| Месячные итоги | Group By: Period, Year, Bucket | Все суммы проверяются, а не только KPI |
| Операционная прибыль | Выручка + себестоимость + коммерческие + управленческие | Расходы уже имеют отрицательный знак |
| Прибыль до налога | Операционная + прочие доходы + прочие расходы | Январь −72, февраль 168, март 288 |
| Перенос убытка | cumulative_sum → maximum(0) → cumulative_max → previous → maximum(разница, 0) | Разбиение Year + Bucket; история сохраняется до расчёта |
| Ставки | Видимая формула 0.25 / 0.02 | Это настройки учебного примера, не налоговые рекомендации |
| Чистая прибыль | PBT + Tax | Проверка всех шести месяцев и общего KPI |
| План и прогноз | Левый Join по Period | Февраль остаётся null; на графике нет выдуманных значений |
| Отчёт и детализация | Публикации Monthly P&L, Net profit total, Source detail | Несколько визуализаций используют одну публикацию |

В этом примере налоговая база явно выбрана из PBT БУ. Выручка НУ показана отдельно.
Это сознательная учебная настройка, а не утверждение о соответствии налоговым правилам
или всем режимам исходного приложения. Для иной базы автор меняет вход накопительного расчёта.
Приоритеты сопоставления и автоматические корректировки исходника не воспроизводятся скрыто:
выбрано строгое соединение по двум ключам, а несопоставленные строки доступны в диагностике.
На реальных книгах необходимо подтвердить ключи, классификацию счетов, знаки и базу налога.

## Как собрать вручную

1. Создать проект, загрузить четыре книги, добавить нужные листы в новый полевой workflow.
2. Настроить границы Accounting. На выходе выбрать «Объединить с…», Realization, два ключа,
   левое соединение и «многие к одному». Повторить с Cost. Просмотреть несопоставленные строки.
3. Добавить вычисляемые поля. Простые условия доступны через «Поле по условию»;
   выражения вводятся в безопасном редакторе, поля вставляются по названиям.
4. Сгруппировать по периоду, году и направлению. Добавить прибыль и последовательность Window v2.
   Для накопительных операций выбрать поле, разбиение и однозначную сортировку Period.
5. Суммировать направления по периоду, присоединить Plan. Опубликовать месячные показатели.
6. Создать отдельный Group By без измерений для общего KPI. Опубликовать его и исходную детализацию.
7. Из карточек результатов создать таблицу, Bar с несколькими сериями, Line и KPI.
   Визуализации не выполняют агрегации: нужные значения уже рассчитаны графом.
8. На дашборде добавить визуализации из списка, переместить и изменить размеры, сохранить.

Повторяемая браузерная сборка: `npm run test:e2e -- e2e/alma-dashboard.spec.ts` в `frontend`.
Книги загружаются через обычный API; граф, публикации, визуализации и размещения создаются формами UI.
Для сохранения демонстрационного проекта установить `NODEBI_KEEP_ALMA_DEMO=1`.
Протокол сохраняется в `test-results`, ссылка на сохранённый пример — `.backups/alma-demo.json`.

## Проверенный объём примера

Граф содержит 28 узлов: 4 источника, 3 Join, 15 вычисляемых полей, 3 Group By и 3 Window.
Три публикации обслуживают пять визуализаций: месячную таблицу, сравнение четырёх серий,
линию чистой прибыли, общий KPI и детализацию исходных записей. Общая чистая прибыль — 693,76.
Браузерная сборка с нуля через формы заняла 79,85 секунды в локальном автоматизированном прогоне.
Это длительность работы теста с заранее известными правилами, а не норматив для экономиста.

## Ограничения и скорость работы

Создание нового графика на готовой публикации требует выбора результата, типа и полей;
общие вычисления, ключи объединения и условия повторно не настраиваются. Это подтверждаемое
сокращение дублирующей настройки. Наиболее сложная часть — первоначальное построение расчёта:
знание структуры книг, ключей, классификации, порядка агрегаций и накопительных операций.
Для экономиста, привыкшего только к Excel, Window и контекст строк требуют обучения.

Время браузерного теста включает автоматические действия и ожидания сохранения. Оно не является
временем работы человека. Проверять скорость экономистов следует отдельно: построение с нуля,
добавление диаграммы к готовым данным, изменение формулы, поиск ошибки Join, восстановление проекта.
Фиксировать время, успешность без помощи, ошибки и обращения к инструкции. Сравнение проводить
на одних данных и одинаковых заданиях с привычным Excel-процессом; порядок заданий чередовать.
До этого испытания проценты ускорения и обещание конкретного времени подготовки отчёта не обоснованы.

Беспристрастная оценка: добавление и размещение графиков на готовом результате — простой этап;
подготовка типового объединения и арифметики — умеренно сложный; первичное проектирование этого
P&L с переносом убытка — сложный и пока не подходит неподготовленному оператору без инструкции.
Ускорение наиболее вероятно при повторном использовании согласованного графа и добавлении новых
представлений. Доказательств, что первый отчёт экономист соберёт быстрее привычного Excel, пока нет.
Пакетная замена книг с историей версий и откатом отложена: обновление источников остаётся отдельной
ручной операцией и требует проверки схем, ключей и настроек чтения.

## Семантика новых операций

Условие с null выбирает ветку Otherwise. Ветви Polars вычисляются векторно: условие не заменяет
безопасное преобразование некорректного текста. `to_number` и `to_date` строгие; для исправления
ошибок используется явный Convert Types с выбранной политикой. `extract` возвращает полное
совпадение регулярного выражения или null. `minimum`/`maximum` сохраняют null; `coalesce` задаёт
замену явно. `round` допускает 0–8 знаков. Calendar создаёт включительный диапазон до 36600 дней.
Window v2 требует однозначного порядка внутри раздела; одинаковые ключи порядка отклоняются.
Диагностика Join показывает ограниченные страницы исходных строк даже при нарушении кардинальности.
