# Ручная сборка дашбордов: обзор и план упрощения

Дата: 2026-09-15. Статус: анализ завершён, переработка предложена, не реализована.

## Вывод

Конструктор позволяет воспроизвести пример, но ручная сборка всех шести экранов
переусложнена для аналитика, который не проектировал сам инструмент. Пользователь
вынужден одновременно разбираться в данных, строить вычислительный граф и вручную
согласовывать настройки экранов. Особенно неудобно сопровождение чужого графа.

Нужна переработка сценария работы поверх существующего движка. Замена стека или
специальные финансовые вычисления не нужны. Явные вычисления следует сохранить,
но их не обязательно постоянно показывать человеку как 168 отдельных карточек.

## Основания и границы анализа

Проверены актуальный сохранённый workflow через API, его финальный снимок, формы
редактора, карточки узлов, формулы, настройки параметров и браузерные сценарии сборки.
Актуальный граф совпадает с проверенным снимком. Результаты:

| Что приходится сопровождать | Количество |
| --- | ---: |
| Узлы подготовки и вычислений | 115 |
| Узлы визуализаций | 53 |
| Все узлы / связи | 168 / 172 |
| Calculated Column / Filter / Window | 27 / 24 / 8 |
| Select Columns / Rename Columns | 6 / 10 |
| Правила переименования / преобразования типов | 34 / 24 |
| Group By / настроенные агрегации | 7 / 20 |
| Дашборды / размещения виджетов | 6 / 55 |
| Параметры workflow / объявления параметров дашбордов | 3 / 9 |
| Привязки параметров / действия виджетов / родительские ссылки | 9 / 20 / 8 |

53 визуализации размещены 55 раз: некоторые используются повторно. Часть сложности
обусловлена самим примером, а часть — выбранной последовательностью сборки. Это не
доказательство, что 168 узлов — минимально возможное количество.

Браузерная автоматизация действительно пользовалась UI, но заранее знала граф,
соответствие колонок и правильные формулы. Поэтому успешная приёмка подтверждает
функциональность, а не самостоятельность и скорость работы обычного пользователя.
Замера времени ручной сборки и исследования с пользователями пока нет; оценки
«за час» или «за день» были бы предположениями.

## Как человек собирал бы это сейчас

### 1. Подготовить исходные данные

Создать проект, загрузить Excel, открыть workflow, добавить Excel Source и выбрать лист.
В настройках источника указать начало заголовка 3, количество строк заголовка 2,
включить номер исходной строки. Проверить preview: заголовки, реальные столбцы,
номер строки, отсутствие строки с итогами среди услуг.

Затем последовательно добавлять узлы из библиотеки. Для каждого выбрать входной узел
в настройках либо соединить порты на canvas, заполнить форму, проверить схему/preview.
Сохранение workflow автоматическое; перед проверкой результата дождаться сохранения.

Нужны выбор/переименование полей, преобразование номера услуги в число с явным
режимом «ошибка → null», отбор числовых строк и непустых услуг, исключение «обоснование».
Очистка названий и заполнение класса задаются формулами. Денежные поля преобразуются
строго; пустые значения заменяются нулём отдельными явными выражениями.

Выбор режима для номера строки не означает разрешение игнорировать ошибочный денежный
текст. Отсутствующий сохранённый результат формулы Excel требует пересчёта книги.

### 2. Получить таблицу услуг и статьи

Создать вычисляемые поля: прямые расходы, неэффективность, косвенные без неё и общий
итог. Общий итог использует исходные косвенные, которые уже включают неэффективность.
Суммы статей и итоговые столбцы Excel не взаимозаменяемы.

Для статей выделить три набора колонок. В каждом выполнить Select → Rename → Unpivot,
сохранить идентификатор услуги и исходного поля, добавить значение с coalesce и
постоянное название вида затрат. Согласовать выходные имена и соединить ветки Union.
Получается несколько повторяющихся цепочек ради одной понятной таблицы «Статьи».

### 3. Построить сводку

От таблицы услуг сделать Group By без измерений для общего итога и количества услуг.
Отдельно сгруппировать по классу; настроить суммы и количество. Для структуры затрат
развернуть три итоговых поля через Unpivot. Для рейтингов поставить Sort и Limit.

Добавить KPI, таблицы и диаграммы как узлы workflow. Для каждого отдельно выбрать
вход, поля, заголовок, формат, точность и ориентацию. Затем перейти на страницу
дашбордов и по одному добавить сохранённые визуализации, переместить, изменить размеры,
нажать «Сохранить дашборд». Даже эта промежуточная сводка первоначально заняла 29 узлов.

### 4. Построить детальные экраны

Объявить три параметра workflow: класс, ID услуги, вид затрат. Добавлять Filter со
ссылкой на параметр только в нужном месте каждой ветки. Для долей и рангов до фильтра
выбранной записи вычислить суммы Window и порядковые номера с сортировкой и ключом
исходной строки. Для некоторых долей соединить статьи с итогами через Join.

Например, доля услуги в классе требует такой цепочки:

```text
Таблица всех услуг
  → Window: сумма «Итого», разбиение по классу
  → Calculated Column: safe_divide(итого услуги, итог класса, 0)
  → Filter: класс = параметр класса
  ├→ Sort → диаграмма сравнения всех услуг класса
  └→ Filter: ID услуги = параметр услуги → KPI выбранной услуги
```

Названия в примере обозначают поля. Текущий редактор вставляет их технические ID.
Если Filter услуги поставить перед Window, знаменатель сузится до одной услуги и
доля станет неправильной. Подсветка услуги на сравнительной диаграмме настраивается
отдельно от фильтра: остальные услуги должны остаться видимыми.

Повторить настройку результатов и визуализаций для «Класс», «Услуга», «Вид затрат»,
«Вид затрат в классе», «Вид затрат услуги». Нулевые статьи и top-ограничения отбирать
после вычисления необходимых полных итогов.

### 5. Связать экраны

На каждом дашборде повторно объявить нужные параметры, их типы, обязательность и
связи с параметрами workflow. Указать узел и поле, откуда выбирать значения.
Для каждой таблицы/диаграммы заранее включить скрытые поля, нужные для перехода.

В настройках перехода выбрать целевой дашборд и сопоставить его параметры полям
нажатой записи, текущим параметрам или константам. Отдельно настроить ссылки назад.
Для выбора услуги использовать её устойчивый ID; одинаковые названия не означают
одну запись. Сейчас прямой селектор показывает номер строки, а не название услуги.

### 6. Проверить и сопровождать

Проверить все экраны, фильтры, знаменатели, сортировки, переходы, восстановление URL и
перезапуск. Для изменения формулы найти узел через поиск, понять его входы, исправить
выражение и проверить затронутые визуализации. Для изменения статьи пройти цепочку
выбора, переименования, Unpivot и схем downstream. Для перехода вернуться в настройки
дашборда; для полей диаграммы — в workflow. Единого маршрута «от виджета к его расчёту»
с объяснением зависимостей сейчас не хватает.

Это приоритеты UX-переработки, не переоценка исправности вычислительного движка.
Открытых воспроизведённых P0/P1 в расчётах этот обзор не выявил. Вероятность ошибок
человека и влияние на время работы требуют проверки с людьми.

## Целевой сценарий

Пользователь видит три рабочих области: **Данные → Расчёты → Дашборды**.
Граф остаётся доступным способом просмотра и редактирования тех же объектов.

1. В «Данных» выбрать заголовки по preview, настроить таблицей имена/типы/пропуски.
2. В «Расчётах» назвать результаты «Услуги», «Статьи», «Итоги классов»; добавлять шаги
   к выбранному результату и сразу видеть изменение данных.
3. Для доли выбрать числитель и явно задать знаменатель: все строки входа, группа
   либо отдельный подготовленный итог. Просмотреть создаваемую цепочку и фильтры.
4. В «Дашбордах» выбрать результат, создать виджет, настроить поля и оформление
   в одном месте. Из виджета открыть источник и цепочку его вычислений.
5. Добавить селекторы и переходы с понятными подписями полей, затем включить просмотр.

В обычном обзоре показывать общую подготовку и шесть именованных групп экранов.
Раскрытие группы показывает все операции и внешние зависимости. Число физических
узлов не является главным показателем удобства: сначала нужно уменьшить число
объектов и деталей, которые человек обязан одновременно держать в голове.

## План поставки

### U0. Зафиксировать сценарии и базовый замер

На копии проекта дать аналитику без доступа к тестовым рецептам: собрать долю в классе,
добавить статью, поменять группировку, настроить переход. Записать время, ошибки,
обращения за помощью и переключения экранов. Отдельно проверить объяснение уже
построенного расчёта. Нужны реальные участники; автоматизация не заменяет этот замер.
Подготовить макеты U1–U3. Результат: протокол и исходные метрики, не обещание времени.

### U1. Сделать существующий граф читаемым

- Имя и краткое содержание на карточке: «Доля в классе», «Сумма по классу»,
  «Услуга = выбранная». Для узлов без смыслового имени добавить редактируемую подпись.
- Фокус на предках/потомках выбранного узла; именованные сворачиваемые группы,
  внешние порты, дерево результатов. Автораскладка по зависимостям только по команде.
- Действие «Добавить следующий шаг» с подключением к выбранному выходу; замена входа
  одной атомарной операцией с прежней проверкой циклов, без промежуточного отключения.
- Перестраиваемые панели вместо фиксированной узкой формы; просматриваемая таблица
  результата рядом с настройкой. Undo/redo для составных действий, без обхода ревизий.

Приёмка: на копии нынешнего графа найти расчёт от виджета, показать его источники и
изменить настройку без поиска технических ID. Группировка и раскладка не меняют данные.
Метаданные групп/подписей сохраняются с ревизией; старые workflow открываются как раньше.

### U2. Упростить поля, формулы и подготовку

- Показывать ссылки в формулах именованными токенами, сохраняя внутри стабильные ID.
  Для одинаковых имён показывать источник; переименование не ломает ссылки. Вставка
  в позицию курсора, подсказки функций, типов и ошибки рядом с выражением.
- Табличная настройка нескольких вычисляемых полей. В первой версии это редактор
  цепочки обычных Calculated Column, а не новый независимый язык или движок.
  Порядок строк явный; поле может зависеть от предыдущих. Изменение применяется атомарно.
- Общая таблица подготовки: выбрать, переименовать, преобразовать типы, указать
  политику пропусков; перед применением показать создаваемые обычные узлы.
- Расширить форму Unpivot выбором групп исходных полей и их подписей. Мастер создаёт
  раскрываемые Select/Rename/Unpivot/Calculated Column/Union; одинаковые статьи сохраняют ID.

Приёмка: подготовить синтетические данные другой предметной области и изменить статью
в примере без копирования ID. Сравнить результат мастера и вручную созданной цепочки.
Редактирование раскрытого графа не должно расходиться с формой: неподдерживаемую
структуру показывать как обычные шаги, не пытаться молча восстановить по старому шаблону.

### U3. Облегчить аналитические операции без скрытой семантики

- Мастера «Доля» и «Место в группе» с явными входом, группой, сортировкой, ключом
  равенства, политикой нуля и областью знаменателя.
- До применения показывать цепочку Window/Calculated Column/Filter либо явное
  соединение с подготовленным итогом. Объяснение: «Знаменатель рассчитан до отбора услуги».
- Показывать параметры, реально влияющие на ветку, и где они применяются; подсветить
  путь расчёта знаменателя. Не выводить бизнес-смысл из названия колонки автоматически.
- Именованные результаты и явное повторное использование одного выхода. Пока без
  отдельного семантического слоя, глобальных мер и автоматического переиспользования
  по совпадению имён: это усложнит правила фильтрации и сопровождение.

Приёмка: доля услуги сохраняет итог класса при смене услуги; доля класса сохраняет
общий итог; сравнение сохраняет остальных участников; ранги устойчивы при равенстве.
Пользователь должен суметь объяснить знаменатель по интерфейсу, не по исходному коду.

### U4. Собрать визуализации и переходы в одном месте

- «Создать виджет» на дашборде: выбрать именованный результат, тип, поля и формат.
  Создаётся обычный visualization node; настройки остаются только в нём.
  «Открыть расчёт» ведёт к точной ветке. Для общей визуализации показать все места
  использования и предложить явное создание копии при независимой настройке.
- «Добавить фильтр» импортирует совместимое объявление workflow, но привязки остаются
  явными. Источник выбора содержит отдельно поле значения и поле подписи: ID услуги
  передаётся, название отображается. Одинаковые названия дополняются классом/ID.
- Настройка перехода непосредственно у виджета: целевой экран и таблица соответствий.
  Мастер предлагает необходимые контекстные поля и показывает изменение перед сохранением.
- Режимы «Редактирование» и «Просмотр», шаблоны сетки для KPI/таблиц/диаграмм. Просмотр
  скрывает служебные панели и ручки размеров, сохраняя фильтры, ссылки и URL.

Приёмка: создать Bar и переход без ручного поиска узлов в библиотеке; название услуги
видно в селекторе, в URL остаётся ID. Изменение параметра не сохраняет граф.
Создание node/widget и изменения нескольких ревизий имеют атомарный контракт либо
восстанавливаемое подтверждённое состояние; двойное нажатие не создаёт дубликаты.

### U5. Перенести пример и повторить приёмку

Сделать резервную копию и работать на копии проекта. Сначала применять только подписи,
группы и представление; расчётные цепочки сокращать лишь при доказанной эквивалентности.
Сравнить все 164 среза, переходы, граф и результаты после перезапуска. Проверить обе темы,
три языка, две вкладки, отмену изменений и восстановление черновика.

Повторить задания U0 с 3–5 аналитиками, не участвовавшими в реализации. Предлагаемые
критерии удобства: минимум 4 из 5 завершают задания без разработчика; медианное время
не менее чем на 40% ниже базового; ни одной незамеченной ошибки знаменателя; ни одного
ручного ввода технического ID. Это цели будущей проверки, а не уже полученные результаты.
Не считать уменьшение количества кликов достаточным при неправильных расчётах.

## Контракты, последовательность и ограничения

Порядок: U0 → U1 → U2 → U3 → U4 → U5. После U1 провести раннюю проверку читаемости,
после U3 — самостоятельную сборку одной доли, не ждать реализации всего плана.

Сохранить FastAPI/Polars/Next.js/React Flow и существующие ограничения ресурсов. Схема,
проверка типов и исполнение по-прежнему используют общие контракты. Мастера создают
обычные узлы, не выполняют финансовые расчёты на frontend и не добавляют специальный API.

Новые сохраняемые метаданные групп, подписи селекторов и составные операции требуют
типизированных контрактов и совместимых значений по умолчанию. Структурные изменения
БД оформлять миграциями; изменения JSON валидировать и документировать. OpenAPI/TS
обновлять вместе. Предусмотреть отсутствие/удаление поля подписи и конфликт ревизий.

В этом обзоре реализация приложения и данные не изменялись. Переработка не отменяет
завершённую функциональную приёмку и не объявляется выполненной заранее. AI-генерация,
смена движка, отдельный финансовый модуль и корпоративные функции в план не входят.
